# 採用業務代行（応募〜採用）要件定義 v0.1

> **位置づけ**：SuguDesk 採用業務代行サービスの要件定義叩き台。
> プロトタイプ第1版（pages/prototype/）の反省を踏まえ、業務フロー → データフロー → 機能要件 → 提供価値 の順で組み直したもの。
> ユーザーフィードバック後に v0.2 を作成し、それを基にプロトタイプ再構築・実装に進む。

---

## 0. スコープ定義

### v0.1 で扱う範囲（応募〜採用の核）
- 求人原稿の管理（媒体別）
- スカウトテンプレ管理・送信実績の集計
- 媒体経由の応募取り込み
- 紹介会社経由の候補者取り込み・管理
- 候補者の進捗管理（書類選考〜面接〜採用判断）
- 媒体・紹介会社別ROI集計
- 月次レポート
- 院長/事務長への通知

### v0.1 で扱わない範囲
- 入職後の定着フォロー
- 採用広報（note・採用ページ運用）
- ドクター紹介会社グリップ強化機能
- 退職予兆AI
- 業種別ベンチマーク（横断統計）
- マルチテナントの権限管理

## 1. ステークホルダー

| 役割 | 概要 | 期待値 |
|---|---|---|
| **院長** | クリニック責任者、採用最終判断者 | 「採用業務から解放される」「結果が見える」 |
| **事務長** | 院長配偶者など、運営担当 | 院長と同等の情報・操作権限 |
| **SuguDeskオペレータ** | サービス提供側、複数院担当 | 効率的に複数院を運用できる |
| 候補者 | 媒体経由・紹介会社経由 | システム外部、SuguDesk側に直接アクセスしない |
| 媒体 | Indeed・ジョブメドレー等 | システム外部、メール・CSV経由でデータ取得 |
| 紹介会社 | マイナビ・レバウェル等 | システム外部、メール・電話で連携 |

## 2. 業務フロー（ユースケース定義）

### UC-1: 求人原稿の作成・媒体掲載
**いつ**：契約初期、または求人内容変更時
**主担当**：オペ（院長/事務長は承認のみ）
**フロー**：
1. オペが院ヒアリング（30分）：求める人材像、訴求ポイント、給与条件
2. オペがAI支援で求人原稿作成（業種別テンプレベース）
3. 院長/事務長が確認・承認
4. オペが各媒体に投稿（フィード対応媒体は半自動）
5. SuguDesk側に「掲載開始」を記録

### UC-2: 媒体への直接応募が発生
**いつ**：候補者が媒体経由で応募
**自動化度**：◎（AI自動取り込み）
**フロー**：
1. 媒体から「応募がありました」通知メールを SuguDesk 専用転送アドレスに転送
2. AIがメール本文をパース：媒体・職種・タイムスタンプ抽出（個人情報除外）
3. 案件として自動登録（ステータス：応募）
4. 院長LINEに通知（「○○媒体に看護師1名応募」）
5. オペが媒体管理画面で詳細確認、必要なら一次対応（媒体内メッセージ）

### UC-3: スカウト戦略の月次設計
**いつ**：月初
**主担当**：オペ（院長/事務長は予算・方向性を承認）
**フロー**：
1. 前月の実績（送信数・開封率・返信率・テンプレ別成果）をレビュー
2. 当月の送信枠を媒体別に配分（看護roo!: 50通、ジョブメドレー: 40通…）
3. 使用するテンプレを選定（A/B/Cパターン）
4. 院長/事務長に計画共有・承認
5. SuguDeskに送信計画を保存

### UC-4: スカウトの実送信（バルク前提）
**いつ**：月内、計画に従って実施
**主担当**：オペ（媒体管理画面で実施）
**フロー**：
1. オペが媒体管理画面で候補者を検索
2. SuguDesk からテンプレを取得（コピー）
3. 媒体管理画面で **同一テンプレを複数候補者に送信**（媒体側UIでバルク送信）
4. **SuguDesk側での「1件ずつ送信完了報告」は廃止**
5. 実績は UC-5 の月次バッチで取り込む

### UC-5: スカウト実績の月次取り込み
**いつ**：月末・月初
**主担当**：オペ
**フロー**：
1. オペが各媒体管理画面でCSVエクスポート
2. SuguDesk管理画面にCSVアップロード
3. AIがCSV解析：
   - 送信数・開封数・返信数を集計
   - テンプレ別パフォーマンス（媒体側でテンプレ識別可能な場合）
   - 個人情報列は除外
4. SuguDeskに月次集計として保存

### UC-6: スカウト返信が発生
**いつ**：候補者からのスカウト返信
**自動化度**：◎（AI自動取り込み）
**フロー**：
1. 媒体から「スカウト返信」通知メール
2. AIパース、案件として自動登録（ステータス：応募 = スカウト経由）
3. オペが媒体管理画面で返信内容確認
4. 院長LINEに通知
5. 必要に応じて面接案内（UC-9）

### UC-7: 紹介会社からの候補者紹介
**いつ**：紹介会社からのメール受信時
**自動化度**：○（AI半自動）
**フロー**：
1. 紹介会社から SuguDesk 専用アドレスにメール（CC or 転送）
2. AIパース：紹介会社識別、職種、媒体内参照IDを抽出（個人情報除外）
3. 案件として登録（媒体 = 紹介会社名、ステータス：応募）
4. 院長LINEに通知（「○○紹介会社から看護師1名紹介、要確認」）
5. オペが詳細を紹介会社側で確認、院長への共有方法を判断

### UC-8: 書類選考
**いつ**：応募・紹介発生後
**主担当**：院長判断、オペが結果入力
**フロー**：
1. オペが院長に書類確認依頼（紹介会社管理画面リンク or 媒体管理画面リンク）
2. 院長が確認・通過/不通過を判断
3. オペがSuguDeskに結果記録
4. ステータス更新：書類通過 or 不採用
5. 通過なら面接調整（UC-9）、不通過なら不採用通知（UC-12）

### UC-9: 面接日程調整
**いつ**：書類通過後
**主担当**：オペが調整
**フロー**：
1. オペが院長カレンダーから空き時間取得（Google Calendar連携）
2. 候補者向けに日程調整リンク発行 or 媒体内メッセージで日程提示
3. 候補者が日程選択
4. 確定後、院長カレンダーに自動登録、リマインド設定
5. 院長LINEに「○○様 面接予定」通知
6. SuguDeskに「面接予定」イベント記録

### UC-10: 面接実施
**いつ**：面接当日
**主担当**：院長、オペが結果入力
**フロー**：
1. 院長が面接実施
2. 院長から結果フィードバックをオペに連絡（LINE/電話/メール）
3. オペがSuguDeskに「面接実施・通過 or 不通過」を記録
4. ステータス更新

### UC-11: 採用判断・採用通知
**いつ**：面接通過後
**主担当**：院長判断、オペが採用通知作成・送信
**フロー**：
1. 院長が採用候補者を決定
2. オペが採用通知書ドラフトをAI生成
3. 院長承認後、媒体経由 or メールで送信
4. 候補者承諾後、SuguDeskに「採用確定」記録
5. 入職日を院長カレンダーに登録

### UC-12: 不採用通知
**いつ**：不採用判断時
**主担当**：オペ代行
**フロー**：
1. オペが不採用通知文をAI生成
2. 院長承認後、媒体経由で送信（候補者の媒体内メッセージ機能）
3. SuguDeskに「不採用通知済み」記録

### UC-13: 紹介会社への要望伝達・フィードバック
**いつ**：随時、または月次
**主担当**：オペ
**フロー**：
1. 院の希望（職種・経験・条件）を整理
2. 各紹介会社にメール・電話で要望伝達
3. 伝達履歴をSuguDeskに記録（紹介会社マスタに紐付け）
4. 紹介結果のフィードバック（「先月紹介の○○さんは面接通過しました」等）
5. 紹介会社別の実績集計（紹介数・採用数・成約率）

### UC-14: 月次レポート生成・配信
**いつ**：月初3営業日以内
**主担当**：オペ生成、院長/事務長閲覧
**フロー**：
1. SuguDeskが月次集計データを準備
2. オペが「AI本文生成」を実行
3. オペがレポートをレビュー・微調整
4. PDFを院長に配信（LINE or メール）
5. 月次MTG（30分）で内容共有

## 3. データフロー

### データ発生源マップ

| イベント | 発生源 | キャプチャ方法 | 自動化度 | DB反映 |
|---|---|---|---|---|
| 応募 | 媒体 | メール通知のAIパース | ◎自動 | 案件作成 |
| スカウト返信 | 媒体 | メール通知のAIパース | ◎自動 | 案件作成 or イベント追加 |
| 紹介会社からの紹介 | 紹介会社メール | メール通知のAIパース | ○半自動 | 案件作成 |
| スカウト送信実績 | 媒体 | 月次CSVアップロード | ○半自動 | 月次集計 |
| 媒体掲載費 | 媒体請求書 | 月次オペ手入力 | ✕手動 | 月次集計 |
| 紹介手数料 | 紹介会社請求書 | 都度オペ手入力 | ✕手動 | 案件に紐付け |
| 書類選考結果 | 院長 | LINE/口頭 → オペ入力 | ✕手動 | 案件のイベント |
| 面接予定 | オペ調整 | Google Calendar連携 | ○半自動 | 案件のイベント |
| 面接結果 | 院長 | LINE/口頭 → オペ入力 | ✕手動 | 案件のイベント |
| 採用確定 | 院長 | LINE/口頭 → オペ入力 | ✕手動 | 案件のイベント |
| 不採用通知済 | オペ | 媒体内送信 → オペ入力 | ✕手動 | 案件のイベント |
| 紹介会社への要望伝達 | オペ | 都度入力 | ✕手動 | 紹介会社マスタにログ |

### 個人情報非保持原則

**SuguDeskに保存しない**：
- 候補者氏名、連絡先（メール・電話）、住所
- 経歴詳細、志望動機本文、自由記述

**SuguDeskに保存する**：
- 媒体内の匿名ID、媒体名、職種
- 集計値、ステータス、イベント時刻
- 院長判断のフラグ的情報

### イベントログモデル（中核思想）

すべての変化を「イベント」として記録：
- 案件作成
- ステータス変更
- 院長判断
- メール受信ログ
- 紹介会社への要望伝達
- 月次レポート生成

→ 後で「あの案件はどう動いたか」が完全に追跡可能。

```

- id, name, specialty, address, contact_info(LINE等)

[Media 媒体マスタ]
- id, name, type (掲載/紹介/スカウト/紹介会社)

- 紹介手数料率
- 契約状況
- 当社からの要望履歴（サブコレクション）

[ScoutTemplate スカウトテンプレ]
- id, clinic_id, name, pattern (A/B/C)
- subject, body
- 業種・職種

[Case 案件] ← 候補者単位、匿名ID管理
- id (内部ID)
- clinic_id, source_id (Media or Agency)
- external_anon_id (媒体内の匿名ID)
- role (職種)
- status (応募/書類選考/面接予定/面接実施/内定/採用/不採用)
- created_at, updated_at

[CaseEvent 案件イベント]
- id, case_id
- event_type (status_change/note/communication)
- from_status, to_status
- memo (個人情報除く)
- recorded_by (system/operator/clinic)
- recorded_at

[ScoutBatch スカウト月次集計]
- id, clinic_id, month
- media_id, template_id
- sent, opened, replied
- データ取り込み元 (csv/email/manual)

[JobPosting 求人原稿]
- id, clinic_id, media_id
- title, body
- last_updated_at

[AgencyRequest 紹介会社への要望]
- id, agency_id, clinic_id
- 要望内容、伝達日、ステータス
- フィードバック履歴

[MonthlyReport 月次レポート]
- id, clinic_id, month
- 集計値, 改善提案, 来月計画
- generated_at, sent_to_clinic_at
```

## 5. 機能要件（v0.1）

### F-1: メール取り込み（応募・スカウト返信）
媒体からの通知メールを自動パース、案件登録 or イベント追加。
- 主要媒体（Indeed、ジョブメドレー、看護roo!、マイナビ等）の通知パターンに対応
- AIで内容パース、個人情報除外
- 失敗時はオペアラート

### F-2: 紹介会社メール取り込み
紹介会社からのメールを準自動取り込み。
- フォーマットがバラバラなのでAIで構造化
- 取り込み失敗・確信度低はオペレビュー必須

### F-3: スカウトテンプレ管理
- テンプレ作成・編集（業種・職種・パターン別）
- 業種別の初期テンプレライブラリ
- AI生成補助（叩き台作成、改善提案）
- **個別送信のUIは不要（オペは媒体側で完結）**

### F-4: スカウト実績取り込み（CSV）
- 各媒体のCSVを月次取り込み
- AI解析で集計値抽出
- テンプレ別パフォーマンスの紐付け（媒体側で識別可能な場合）

### F-5: 案件進捗管理（カンバン）
- 案件のステータス可視化（応募/書類/面接予定/面接実施/内定/採用/不採用）
- ステータス変更（オペ操作 or 自動連動）
- 案件詳細にイベント履歴
- 検索・フィルタ（媒体・職種・期間）

### F-6: 院長判断のイベント記録
- 書類選考結果、面接結果、採用判断、不採用通知済 をオペが入力
- 入力時にステータス自動連動

### F-7: 紹介会社管理（**v0.1 で必須追加**）
- 紹介会社マスタ
- 紹介会社別の実績集計：
  - 紹介数（期間別）
  - 書類通過率・面接通過率・採用率
  - 紹介手数料合計
  - 早期離職率（v0.2で）
- 紹介会社への要望履歴
- 紹介会社別のフィードバック・対応ログ

### F-8: 月次レポート生成
- データ集計（媒体・紹介会社・スカウト・案件進捗）
- AI本文生成・改善提案
- レポート編集・PDF出力
- 院長/事務長への配信

### F-9: 院長/事務長への通知
- 重要イベントのLINE通知（応募・スカウト返信・面接予定・採用確定等）
- 月次レポート配信

### F-10: 求人原稿管理
- 求人原稿の作成・編集
- 媒体別カスタマイズ
- 投稿履歴管理

### F-11: 媒体・紹介会社ROIダッシュボード
- 媒体別の応募・採用・コスト・CPA・CPHを可視化
- 紹介会社別の同等指標
- 期間比較

## 6. 提供価値（院長/事務長視点）

### 院長/事務長が見るもの
1. **採用ファネルの可視化**：応募→書類→面接→採用の数字、媒体・紹介会社別比較
2. **媒体別ROI**：どこが効率いいか、予算配分の最適化提案
3. **紹介会社の比較**：どこが質の高い候補者を出すか
4. **スカウト活動の成果**：送信→返信→面接→採用のパフォーマンス
5. **進行中の案件**：今何件が面接予定で、何件が判断待ちか
6. **総コスト把握**：媒体費＋紹介手数料＋SuguDesk費を統合

### 院長/事務長がやること（最小化）
1. 求人原稿・スカウト文面の承認（月数回）
2. 書類選考の通過/不通過判断（候補者発生時）
3. 面接実施
4. 面接後の結果共有
5. 採用判断
6. 月次レポート確認・MTG

### 院長/事務長がやらないこと
- 媒体管理画面ログイン
- 求人原稿・スカウト文の作成
- 応募者・候補者への一次返信
- 媒体別効果計算
- 紹介会社との折衝
- 不採用通知作成
- スカウト送信
- 個人情報の取り扱い

## 7. 非機能要件

### 個人情報
- 候補者の個人情報は保持しない
- 媒体内匿名IDのみ参照
- 例外：採用確定後の入職者情報（連絡先1項目）は最小限・期限付き保持（v0.2 で扱う）

### 通知
- イベント発生から院長LINE通知まで30分以内
- 月次レポートは月初3営業日以内に配信

### 媒体規約
- 自動化は規約遵守の範囲内
- スクレイピング・ボットアクセスはしない
- 公式提供のCSVエクスポート・メール通知を活用

### 法規制
- 個人情報保護法：個人情報非保持の設計でリスク回避
- 有料職業紹介事業の許認可不要：業務代行のみ、紹介マッチングはしない
