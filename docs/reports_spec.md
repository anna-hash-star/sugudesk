# SuguDesk レポート／改善チェックシート 仕様

最終更新: 2026-06-15

このドキュメントは、カスタマーサクセス（CS）の運用をAI駆動で自動化しつつ、
「弊社がクリニックとコミュニケーションを取ること自体の価値」を残すための、
**月次の成果物（レポート・改善チェックシート）と管理画面の仕様**をまとめたものです。

- **前半（Part 1）**: 非エンジニア向けの全体像。まずここを読めば全体がわかります。
- **後半（Part 2）**: エンジニア向けの定義（スキーマ・状態遷移・プラン別挙動）。

---

# Part 1. 全体像（非エンジニア向け）

## 1-1. クリニックに渡す「3つのお届けもの」

毎月クリニックに渡すものは3種類だけです。

### ① 簡易レポート（ライト向け）
「今月こんな感じでした」を**メール本文で数行**で伝えるもの。グラフなし・30秒で読める。
- 今月の会話数（先月比）
- AIで解決できた割合（回答率）
- 電話に回った件数
- よく聞かれた話題トップ5
- AIが答えきれなかった質問の件数

### ② 月次レポート（スタンダード以上向け）
**実物 = ルナ様に出している「チャットボット運用レポート（第3回）」**。
MTGで使える資料で、数字・傾向に加えて**示唆と提案**まで入る。
- 回答率の推移と改善効果
- 曜日別・時間帯別・話題別の傾向
- 「この質問が増えている → HPにこう一言足すと問い合わせが減る」という提案
- 修正シートの進捗

### ③ 改善チェックシート（全プラン共通）
**実物 = きむら内科様に送っている「確認シート」（スプレッドシート）**。
「患者さんからこういう質問が来たが、AIにこう答えさせてよいか？」をクリニックに確認する表。
クリニックは「OK」「これは違う、こう答えて」と**埋めて返すだけ**。

> ②③はすでに手運用の実物がある。ゼロから作るのではなく「今の手作業を仕組みで楽にする」話。

## 1-2. 誰が・何をやるか

今はCS担当が全部手でやっている。それを **機械にやらせる部分** と **人が残る部分** に分ける。

**機械が自動でやること（今まで手作業）**
- 先月の会話ログを全部読んで分類する
- レポートの数字・グラフ・表を作る
- 「この質問が◯件来てます。HPにこう書くといいかも」という**示唆の下書き**を作る
- チェックシートに載せる質問を拾い、**区分（①情報確認／②要否判断…）に仕分け**し、答えの下書きまで入れる

**人（CS）が残ること — 2つだけ**
1. **確認**: 機械の下書きを見て「OK」「ここは違う」とチェック・手直し
2. **送る**: クリニックにメールで送る（ライトは機械が自動送信でもOK）

> 「弊社がコミュニケーションを取ること自体が価値」はここで守られる。
> 作る作業から人を解放し、"確認して送る・必要なら一緒に話す" という人にしかできない所に人を残す。

## 1-3. 1ヶ月の流れ

```
月初  →  機械が「レポート下書き」と「チェックシート」を自動で作る
  ↓
CSが中身を確認して、必要なら手直し           ← 人①
  ↓
クリニックに送る（ライトは自動でもOK）          ← 人②
  ↓
クリニックがチェックシートに「OK / こう直して」を記入して返す
  ↓
その回答をもとに機械がFAQの直し方を下書き → CSが承認 → 反映
  ↓
「直した効果」が翌月のレポートに「改善しました」と出る
```

最後の輪が重要。**クリニックが協力する → 数字が良くなる → レポートで見せる → また協力したくなる**
という良い循環を作る（ルナ様レポートの「貴院のご回答→改善効果」がこれ）。

## 1-4. 大事な前提

- クリニックとのやり取りは **今までどおりメール＋スプレッドシート** のまま。
- アプリ内に凝った画面を作って先方に触ってもらう、はやらない。
  イメージは「**システムがメールでレポートとスプシのリンクを送る**」。
- だから管理画面は **裏方**（下書きを作る → CSが確認 → 送る → 返ってきた回答を取り込む）に徹する。

# Part 2. 定義（エンジニア向け）

## 2-0. データソース

既存の会話ログ分類フィールドを源データとする（`pages/[client].js` / Google Sheets 由来）:
`topic_type`, `menu_category`, `is_phone_escalation`, `improvement_action`,
`priority`, `retrieved_faqs`, `selected_faq_id`, 類似FAQ有無, 日別①〜⑤件数・架電件数。

- **回答率** = AIがエスカレーション（電話誘導）なしで完結できた割合。本仕様の中核KPI。
- 期間は「対象月」または「レポート対象期間（例: 4/17〜5/14）」単位。

## 2-1. 簡易レポート `simple_report`（ライト）

メール本文として成立するプレーンテキスト。CS確認はスキップ可、システム自動送信を既定とする。

| フィールド | 型 | 内容 / 算出 |
|---|---|---|
| `period` | string | 対象月（例: 2026-05） |
| `total_conversations` | int | 会話数 |
| `mom_delta_pct` | float | 前月比 % |
| `answer_rate` | float | 回答率＝(全会話−電話誘導)/全会話 |
| `phone_escalations` | int | 電話誘導件数 |
| `top_topics` | array<{name, count}> | よく聞かれた話題Top5（`topic_type`） |
| `unanswered_count` | int | AIが答えきれなかった件数（チェックシート区分①②の数） |
| `check_sheet_url` | string | 改善チェックシート（スプシ）のリンク |

月次レポートのサブセット（`insights`・期間比較マトリックスを省いた軽量版）。

## 2-2. 月次レポート `monthly_report`（スタンダード以上）

ルナ様「運用レポート（第3回）」の実構造に準拠。

### メタ＋アジェンダ
| フィールド | 内容 |
|---|---|
| `clinic_name`, `report_no`, `period_start`, `period_end`, `days` | ヘッダ |
| `agenda[]` | MTGアジェンダ（①利用状況と改善効果／②患者傾向の示唆／③会話例／④修正シート進捗）。テンプレ＋AI要約 |

### 1. 利用状況の推移 `usage_trend`
| ブロック | スキーマ |
|---|---|
| `headline_rate` | 回答率トレンド（例: 81.2→82.8→86.7、導入以来 +5.5pt） |
| `summary_metrics[]` | 行＝{指標, 期間別値…, 変化}。指標＝総メッセージ数／日平均／回答率／診療時間外利用率 |
| `weekly_answer_rate[]` | {週, 件数, 回答率} |
| `improvement_examples[]` | {menu, before_rate, after_rate, delta, before_quote, after_quote} ＝「貴院のご回答→改善効果」 |

### 2. 患者様の傾向 `patient_trends`
| ブロック | スキーマ |
|---|---|
| `dow_dist[]` | {曜日, 件数, 週平均, 回答率} |
| `hour_dist[]` | {時間帯, 件数, 構成比, 回答率} |
| `per_clinic[]` ※プレミアムのみ | {院, 期間別[件数, 回答率]} |
| `topic_dist[]` | {トピック, 件数, 構成比, 回答率} |
| `menu_matrix[]` | {メニュー, 期間別[件数, 回答率]}（3期間比較） |
| `insights[]` | **{title, body, suggestion}** ＝「示唆①〜④＋→提案」。頻度×回答率×時間帯から自動抽出→LLMで提案文生成 |

### 3. 会話例 `conversation_examples[]`
`{title, turns, escalated(bool), excerpt, highlight, user_feedback}` — AIが良い回答をできた代表例。
**ターン数は問わない**（1往復の的確な回答も、複数往復の完結例も含む）。

- `turns`: 往復数（1でも可）
- `escalated`: 電話誘導の有無（false＝AIで完結）
- `user_feedback`: 患者の評価（enum: `good`/`bad`/`none`）。**goodは「良い回答だった」の最も確かな証拠**
- `highlight`: その例の見どころ（enum想定）
  - `単発的確`: 1往復で正確・十分な回答ができた
  - `マルチターン完結`: 複数往復をエスカレなしで処理しきった
  - `難問対応`: 答えにくい質問に適切に対応した

抽出基準（優先順）:
1. **患者がgoodボタンを押した会話**（最優先シグナル）
2. 電話誘導なし＋回答が正確・十分（類似FAQヒット or 高信頼回答）

上記から偏りなく数件選ぶ（単発・マルチ両方を必ず含める）。
※ 患者のgood/badボタンは**新管理画面で実装予定**。押下ログを蓄積し、会話例の最優先シグナルとして使う。
　 同フィードバックは改善チェックシートの優先度づけ（bad集中＝要改善）にも活用する。
　 実装までの暫定期間は 2（電話誘導なし＋高信頼回答）のみで選定。

### 4. 修正シートの進捗 `correction_progress`
| フィールド | 内容 |
|---|---|
| `cumulative` | {累計件数, 貴院回答分, 弊社単独分, 回答率寄与} |
| `new_items` | {件数, `by_section[]`＝{セクション, 件数, 対応状況}, `key_questions[]`＝特にお伺いしたい点} |

`by_section` は改善チェックシートの行を領域でグルーピングした集計ビュー。
レポートとチェックシートは同一データから生成される関係。

## 2-3. 改善チェックシート `improvement_check_sheet`（全プラン共通）

きむら内科「確認シート」準拠。**スプレッドシートのまま運用**（先方記入面）。1行＝1改善候補。
**2層構造**で持つ:

- **社内データ（フル）**: 6区分・優先度・ステータス等すべてを保持。CS/システムが使う。
- **先方ビュー（簡易）**: 上記から「要対応（①②）」だけを抽出し、操作を○/直すの1択に単純化したもの。クリニックはこれだけを見る。

### (a) 社内データ（フルスキーマ）
| 列 | 型 / 語彙 | 記入者 | 説明 |
|---|---|---|---|
| `no` | int | 自動 | 連番 |
| `category`（区分） | enum: `①情報確認`/`②要否判断`/`③FAQ済み`/`④対応不要`/`⑤対応済み`/`⑥システム` | システム/AI | **内部ラベル。先方には見せない** |
| `question` | text | AI | 患者様の質問（原文 or 代表例） |
| `occurrence_count` | int | AI | 当月の発生件数 |
| `priority` | enum: `高`/`中`/`低` | AI | 高＝売上直結／緊急／頻発。bad集中も加点 |
| `current_ai_answer` | text | AI | 現在のAI回答（or「回答できず」） |
| `proposal`（対応案） | text | AI | **AIにこう対応させたい、という案**（回答ドラフト or 対応方針）。先方ビューに出す |
| `client_decision`（ご判断） | enum: `OK`/`直す`/`未確認` | クリニック | 先方記入。○か直すかの1択 |
| `client_note`（修正・補足） | text | クリニック | 「直す」のとき記入 |
| `cs_status`（社内） | enum: `未対応`/`確認中`/`回答待ち`/`FAQ反映済`/`対象外` | CS | |
| `note` | text | CS | 対応メモ |
| `reflected_at` | date | 自動 | FAQ反映日 |

### (b) 先方ビュー（簡易・要対応のみ）
区分①②の行だけを抽出。先方に見せる列はこれだけ:

| 患者さんの質問 | AIの対応案 | ご判断 | 修正・補足 |
|---|---|---|---|
| `question` | `proposal` | `OK` / `直す` | `client_note`（直すときのみ） |

- 区分①も②も先方の操作は同じ＝「**この対応案でOKですか？ → OK / 直す**」の1択。
- 「①情報確認」「②要否判断」等の用語は**一切出さない**。
- ③④⑤⑥は先方ビューに出さない。出すなら別枠「今月のご報告（対応不要・読むだけ）」として畳む。

### 区分の自動判定（3つの出どころに分ける）
全部を硬いルールで決めず、**確実に決まるもの／バグ／意味判断**の3系統に分ける。

| 系統 | 区分 | 決め方 | 信頼度 |
|---|---|---|---|
| 在庫照合 | ③FAQ済み / ⑤対応済み | FAQ在庫を突合（類似FAQあり／当月反映済み） | 高（機械的） |
| シグナル検知 | ⑥システム | エラー・不具合シグナルの検知（別ロジック） | 高 |
| 意味判断（LLM） | ①情報確認 / ②要否判断 / ④対応不要 | LLMが凡例の定義文で分類。既存フィールド（`menu_category`等）は"ヒント"として渡すのみ | 中→CS確認必須 |

**安全装置:**
- **迷ったら①②に倒す（surface優先）。** 先方に確認すべき質問を③④に誤分類して隠す事故を防ぐ（隠す誤りのコストが非対称に大きいため）。確信度の低い③④は必ずCSレビューに上げる。
- 自動分類は「下書き」、確定は**CS確認（人①）**が最終ゲート。

※ クリニック発の要望（them→us）は別エンティティ `client_request` として同じステータス語彙で受け、チェックシートに合流。

## 2-4. 管理画面（裏方コンソール）

「概要／会話ログ」タブの隣に **「月次レポート」タブ** を追加。先方とのやり取り面はメール＋スプシのまま。

### レポート単位の状態遷移
| 状態 | アクション | 担当 |
|---|---|---|
| `生成済(下書き)` | レポート・示唆・回答ドラフトをレビュー／編集 | CS（①） |
| `確認済` | 「送付」＝レポートをメール／PDF＋修正シートのスプシリンクを送信 | CS or システム（②） |
| `送付済` | — | — |
| `取込待ち` | スプシ「ご回答欄」記入を検知→取込→FAQ差分ドラフト生成 | システム→CS（③） |
| `完了` | FAQ反映済 | — |

### プラン別の既定挙動
| プラン | レポート | CS確認 | 送付 | 院別セクション | MTG |
|---|---|---|---|---|---|
| ライト | 簡易（テキスト） | スキップ可 | システム自動送信 | — | なし |
| スタンダード | 月次 | 必須 | CSがボタンで送信 | — | 必要時 |
| プレミアム | 月次 | 必須 | CSがボタンで送信 | あり（`per_clinic`） | あり |
