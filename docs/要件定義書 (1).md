## 1. プロジェクト概要

### 1.1 プロダクト概要

SuguDeskは、**クリニック・病院向けのAI受付SaaS**である。「医療の問い合わせを、完全に解決する」をミッションとし、AIチャットボットによるFAQ自動応答と会話ログ分析ダッシュボードを提供する。

### 1.2 現状

- **導入済み医療機関**: ルナレディースクリニック、AdeB、泉崎審美歯科、みかさ美容クリニック（有料契約）
- **準備中**: 細木病院、きむら内科クリニック
- **現行スタック**: Dify（チャットボット）+ Google Sheets（データストア）+ Next.js（ダッシュボード）
- **課題**: Google Sheetsのスケーラビリティ限界、Dify依存、ハードコード認証、運用属人化

### 1.3 本プロジェクトの目的

現行のDify + Google Sheets構成から、**GCPベースの自社基盤**へ移行し、100院規模へスケール可能なプラットフォームを構築する。

### 1.4 フェーズ構成

| フェーズ | 内容 |
|----------|------|
| Phase 1 | 現行機能のリプレイス + 基盤構築 |
| Phase 2 | 付加価値機能の追加 |

### 2.2 技術スタック

**アーキテクチャ方針（A: 単一バックエンド経由）:** すべてのDBアクセスはC#バックエンド（EF Core）に集約し、Next.jsはUIとServer Actionsのみを担う。フロントエンドはバックエンドAPIを型安全に呼び出す（`openapi-typescript` + `openapi-fetch`）。フロントエンド側のORMは採用しない。

**バックエンド実装方針（CQRS-lite）:** バックエンドは read / write の責務を論理的に分離する。write 側は `Command` + `Handler` を基本とし、1ユースケース = 1トランザクション境界で処理する。read 側はドメインモデルへ無理に寄せず、UI 要件に合わせた `Query Service` または read model を返す。DB やデプロイを read / write で物理分離する段階的な CQRS は現時点では採用しない。

**メッセージディスパッチ方針:** in-process mediator として `Mediator`（martinothamar/Mediator）を第一候補とする。`MediatR` は商用ライセンス前提となったため新規採用の第一候補にはしない。`Pipeline Behavior` は入力検証・ロギング・トランザクション境界のような横断関心事に限定し、HTTP 固有の `ProblemDetails` 変換や対象依存の認可・監査詳細生成を過度に隠蔽しない。

## 3. 機能要件 — Phase 1（現行リプレイス + 基盤構築）

Phase 1は現行Dify + Google Sheets構成のリプレイスを目的とし、既存の稼働中クリニックへのサービス継続を保証する。

### 3.1 INF: インフラ & 基盤

#### INF-1: GCPプロジェクト設定

Cloud Run, Cloud SQL (PostgreSQL + pgvector), Cloud Load Balancing, Cloud Armor, Firebase Auth の構築。

#### INF-2: CI/CD

GitHub Actions → Cloud Run デプロイ、Vercel自動デプロイ。ステージング・本番の2環境構成。

#### INF-3: DBスキーマ設計

マルチテナント対応スキーマ設計（Entity Framework Core マイグレーション管理）。pgvector拡張のセットアップを含む。DBアクセスはすべてC#バックエンド経由のため、マイグレーションはEF Coreに一本化する。

**エンティティ一覧とリレーション:**

```
tenants（契約・課金）
  ├─1:N─ clinics（院。全運用設定を持つ）
  │         └─1:N─ faqs（FAQ + ベクトル）
  ├─1:N─ users（管理画面ユーザー）
  │         └─N:M─ user_clinics（clinic別アクセス権）
  └─1:N─ conversations（会話セッション）
              └─1:N─ messages（Q&A + 診断ログ + 分類結果）

specialty_templates（診療科テンプレート ← clinicが選択）
widget_configs（Widget設定 ← clinicに1:1）
audit_logs（変更履歴 ← FAQ/プロンプト/管理操作）
```

**tenant / clinic の責務分離:**

| レイヤー | 責務 | 主なデータ |
|---------|------|----------|
| `tenants` | 契約・課金・組織管理 | 組織名、プラン、請求情報 |
| `clinics` | **全運用設定** | 診療科テンプレート選択、電話番号、診療時間、LINE URL、非対応診療、カスタム指示、多言語設定、FAQデータ |

- tenantは薄い組織レイヤー。プロンプト設定・電話番号等の運用設定は全てclinic単位
- 理由: 同一テナント内でも院ごとに診療科・電話番号・診療時間が異なりうる（例: 美容クリニック+歯科を運営する医療法人）
- グループ院の共通FAQは`is_common=true`の仮想clinicとしてモデル化

**分類結果のモデル:** messagesテーブルに埋め込み（常にメッセージとセットで参照されるため）。分類ステータス（pending/done/error）で非同期バッチの進捗を管理。

**監査ログ（audit_logs）:** FAQ・プロンプトなど回答品質に直結するデータの変更履歴を記録。

| 対象 | 記録内容 |
|------|---------|
| FAQ変更 | 作成/編集/削除、変更前後の値、操作者、日時 |
| プロンプト変更 | テンプレート編集/カスタム指示変更、変更前後の値、操作者、日時 |
| 管理操作 | テナント作成、ユーザー権限変更、Widget設定変更等 |

**テナント分離:** RLS（Row Level Security）でテナント間のデータ分離を実現。

#### INF-4: 監視設定

- Sentry統合（エラートラッキング）
- Cloud Monitoring / Logging
- Uptime Check（死活監視）

#### INF-5: ローカル開発環境

Docker Compose: PostgreSQL + pgvector のローカル環境構築。

### 3.2 F1-1: チャットWidget

クリニックHPに埋め込むAIチャットボット。現行Difyの機能をリプレイスする。

#### F1-1-1: チャットAPI（RAGパイプライン）

**現行Difyワークフローの処理フロー（リプレイス対象）:**

```
ユーザー入力
  ↓
① 言語判定（Code）── 日本語以外 → 固定メッセージ返却 → 終了
  ↓（日本語）
①-b 個人情報マスク（Code）── 電話番号・メールアドレスをルールベースでマスク
  ↓
② 院選択判定（Code）── グループ院の場合、院名選択を検出
  ├─ 院名選択あり → 確認メッセージ返却 → 終了
  └─ 通常質問 ↓
③ クエリ正規化（LLM）── ユーザー発話をFAQ検索に最適化した短文に変換
  ↓
④ FAQ検索（Knowledge Retrieval）── 院別KBからHybrid検索（top_k=5）
  ↓
⑤ 回答生成（LLM）── FAQ検索結果を基に回答を生成（会話履歴3ターン参照）
  ↓
⑥ 回答表示 → 履歴作成（Code）→ Webhook（ログ記録）
```

**新基盤での実装:**

- ①言語判定: ルールベース（正規表現）で実装。テナント設定で多言語対応のON/OFF
- ①-b 個人情報マスク（二段構え）:
  - 前段（ルールベース）: 電話番号・メールアドレスを正規表現で検出しマスク。LLM送信前に実行
  - 後段（LLM）: ③クエリ正規化のプロンプトに「氏名・住所等の個人情報をマスクせよ」を組み込み、ルールベースで検出困難な個人情報をLLMで処理。追加のAPI呼出なし
  - マスク後のテキストのみをDB保存する
- ②院選択: グループ院テナントのみ有効。選択肢はWidget設定から取得
- ③クエリ正規化: LLMによる正規化。プロンプトは3層構造（後述F1-3-3）
- ④FAQ検索: pgvectorによるHybrid検索（キーワード0.3 + ベクトル0.7、top_k=5）
- ⑤回答生成: LLMによる回答生成。プロンプトは3層構造。会話履歴は直近3ターン
- ⑥ログ記録: Cloud SQLに直接書き込み（Webhook不要）

**追加機能（現行にない新基盤固有）:**
- SSEストリーミング
- テナント認証（widget_key）
- テナント/IP単位のレート制限

**診断ログ記録:**
- `normalized_query`: 正規化後のクエリ
- `retrieved_faqs`: FAQ検索結果（スコア付き）
- `selected_faq_id`: 回答に使用したFAQ
- `is_phone_escalation`: 電話誘導フラグ
- `escalation_reason`: 誘導理由

**LLMモデル選定:** ベンチマークで決定（EMBタスクと併せて実施）。現行はOpenAI gpt-4.1（正規化）+ gpt-5.4（回答生成）。移行先候補はVertex AI Gemini Flash/Pro。同一プロンプト+FAQデータで品質比較を行い決定する。

**要件との差分:**
1. **2段階LLM維持**: 現行Difyの調査により、クエリ正規化LLMは検索精度に重要な役割を果たしていることが判明（医療用語の概念統合、文脈補完等）。当初の「1段階に変更」方針を撤回し、正規化+回答生成の2段階を維持する
2. **セッション管理 → クライアントメモリ方式（サーバーステートレス）**: 医療系のため患者入力がlocalStorage等に残るリスクを回避。業界標準方式（Intercom/Tidio等）

**リスク:**
- SSE + Cloud LB + Cloud Armorの組み合わせでタイムアウト・バッファリング問題が発生する可能性あり
- OpenAI → Vertex AI切替による回答品質の低下リスク（ベンチマークで評価）

#### F1-1-2: チャットWidget UI

**機能:**
- scriptタグ+iframeによる埋め込み（CSS完全分離）
- フローティングボタン → チャット画面展開
- メッセージリスト + 入力エリア
- SSEストリーミング表示
- テーマカスタマイズ（テーマカラー・アイコン画像）
- クイックリプライボタン（初回表示の選択肢）
- オープニングメッセージ
- AI免責文・利用規約・プライバシーポリシー表示
- フォールバック時の電話番号表示
- モバイル対応

**要件との差分:** scriptタグ+iframeハイブリッド方式に決定。Intercom/Drift/Crisp等の業界標準方式。CSS分離が完全でクリニックサイト（WordPress/Wix/独自CMS等）との干渉リスクがゼロ。設置もscriptタグ1行で完了。

**リスク:** 一部CMSのiframe制限、モバイルでのposition:fixed挙動差、z-index競合等の環境依存問題（+1-2日）

**備考:** 3-5件のクリニックサイトでの実機検証が必要

#### F1-1-3: グループ院対応

**機能:**
- チャット開始時に院選択フロー（ボタン形式）
- 選択された院に応じてFAQ検索対象を切り替え
- 院未選択の場合は共通FAQで回答または院選択を促す

**備考:** 既存テナントで稼働中のためPhase 1必須

#### F1-1-4: 会話分類（自動）

**現行仕様（GAS）:** Google Apps Scriptが1分おきにGoogle Sheetsをポーリングし、未分類行をgpt-4o-miniで分類してシートに書き戻す非同期バッチ方式。

**新基盤での実装:**
- 回答生成後にOutboxテーブルへ書き込み
- Cloud Scheduler + Cloud Run Jobsで非同期バッチ分類
- LLMで以下を自動分類:

**分類項目（現行GASプロンプトから移植）:**

| 項目 | 値 |
|------|-----|
| `topic_type` | 料金・支払い / 予約・変更・キャンセル / メニュー・対応可否・相談 / 診療時間・休診日・営業日 / 保険診療・保険適用可否 / 処置後経過・副作用 / クリニック情報（医師・設備等） / アクセス・駐車場・交通 / 処方薬・薬の飲み方・副作用 / 検査結果・検査方法 / あいさつ・雑談・ノイズ / UI操作 / その他 |
| `menu_category` | テナントの診療科に応じて可変（例: 婦人科→ピル・避妊/人工妊娠中絶/性病検査等、美容→施術名ベース） |
| `is_phone_escalation` | true: FAQ未ヒットで電話定型文を返したケースのみ / false: 何らかの情報提供があった場合 |
| `improvement_action` | 正常回答 / FAQ追加 / FAQ修正 / 正規化改善 / 検索精度改善 / 対応不要 |
| `priority` | high（頻出FAQ追加）/ medium（FAQ修正・精度改善）/ low（正常回答・対応不要） |
| `similar_faq_exists` | true/false |
| `note` | 1文の補足メモ |

**要件との差分:**
- 要件ではPhase 2（F2-2）の範囲だが、Phase 1に移動。理由: 現行GASで稼働中の機能であり、ダッシュボードの集計に必須
- 確認事項の回答は「都度」だったが、現行は非同期バッチであり、ユーザー応答レイテンシへの影響を考慮し**非同期バッチを維持**する

**備考:** 分類プロンプトは現行GASのプロンプトをベースに移植。`menu_category`の選択肢はテナントの診療科に応じてカスタマイズ可能にする。

### 3.3 F1-2: テナント管理画面 — 顧客向け

#### F1-2-1: 認証 + マルチテナント

**機能:**
- Firebase Auth（メールアドレス+パスワード）
- ログイン/ログアウト/セッション管理
- RBAC（Admin / Tenant Admin / Tenant User）
- impersonation機能（社内管理者がテナント / クリニックのコンテキストへ切り替え）
  - tenant / clinic 単位の代理セッション。代理先ユーザーで再ログインしない
  - 社内管理者の全権限は代理コンテキストに流さず、代理先スコープに閉じた限定権限で実行する
  - 監査では `actor`（実操作者 = 社内管理者）と `acting_as`（代理先 tenant / clinic）を分離して記録する
  - 代理開始・終了を `audit_logs.action = 'impersonation'` で明示的に記録し、UI 上も「代理中」表示を強制する
- 認可は二段構えで扱う
  - ミドルウェアで「認証済みか」「admin / tenant admin / tenant user のどの大分類ロールか」「代理セッションが有効か」のような粗い認可を先に判定する
  - 対象データに依存する認可（例: 対象 clinic が現在の tenant / clinic コンテキストに属するか、対象操作が代理権限で許されるか）は Application 層 / Domain 層で再判定する
- バックエンド write 側は `Command` + `Handler`、read 側は `Query Service` を基本とする `CQRS-lite` を採用する
- `Pipeline Behavior` で共通化するのは入力検証・ロギング・トランザクション境界までを基本とし、認可詳細や監査詳細をすべて自動化しない

**要件との差分:** F1-2（テナント管理画面）とF1-3（社内管理画面）を1つのNext.jsアプリに統合（impersonation方式）。共通コンポーネント（ログ閲覧、FAQ表示等）の二重実装を回避。

#### F1-3-3: システムプロンプト管理

**3層プロンプト構造:**

Difyワークフロー調査（Luna: 婦人科、AdeB: 美容皮膚科）により、プロンプトを以下の3層に分離する設計を確定。実行時に3層を結合して最終プロンプトを生成する。

```
最終プロンプト = ① 共通ルール + ② 診療科テンプレート + ③ テナント固有情報
```

**① 共通ルール（全テナント共通、exmoreが管理）:**
- 基本姿勢（「判断」ではなく「説明」）
- 根拠制限（answerの範囲内のみ、推測・一般論禁止）
- 禁止事項（ハルシネーション防止、内部用語禁止）
- 候補選択ルール（原則1件、条件付き2件）
- トピック一致必須ルール
- URL出力ルール（Markdownリンク形式）
- 出力フォーマット（です・ます調、改行、箇条書き）
- 電話案内フォールバックの枠組み

**② 診療科テンプレート（診療科別、exmoreが管理）:**

正規化プロンプト・回答生成プロンプトそれぞれに診療科固有のルールを定義。

| 診療科 | 正規化の特徴 | 回答生成の特徴 |
|--------|-------------|---------------|
| 婦人科 | 医学用語マッピング（生理ずらす→月経移動等）、他院検査→処方の強制寄せ、複数相談検出 | 医学的判断フォールバック（診察誘導+LINE予約案内）、スコープ一致ルール |
| 美容皮膚科 | 悩み語保持重視（施術名への推測変換禁止）、入力タイプ分類(A-G) | 施術名未確定時の強制ルール（施術固有FAQを使用禁止）、料金案内ルール |
| 歯科 | （将来追加） | （将来追加） |
| 内科 | （将来追加） | （将来追加） |

**③ テナント固有情報（テナントごと、DB管理）:**
- `clinic_name`: クリニック名
- `phone`: 電話番号（フォールバック文に挿入）
- `line_url`: LINE予約URL（該当テナントのみ）
- `hours`: 診療時間
- `excluded_services`: 非対応診療の一覧（例: 「乳がん検診、不妊治療は行っていません」）

- `language_support`: 多言語対応設定（ON/OFF + 対応言語）

**管理画面の機能:**

- テナントごとの設定: テンプレート選択、固有情報の入力、個別指示の編集

### 3.6 EMB: Embedding・LLM品質ベンチマーク

  - 正規化精度（用語マッピングの正確性、文脈補完の妥当性）

**リスク:** Embedding精度またはLLM品質が想定以下の場合、プロンプトチューニングまたはモデル再選定の追加工数が発生

### 5.1 パフォーマンス

### 5.2 LLMモデル移行

| 処理 | 現行（OpenAI） | 移行先候補（Vertex AI） | 決定方法 |
|------|---------------|----------------------|---------|
| クエリ正規化 | gpt-4.1 | Gemini Flash or Gemini Pro | ベンチマーク |
| 回答生成 | gpt-5.4 | Gemini Flash or Gemini Pro | ベンチマーク |
| 会話分類 | gpt-4o-mini | Gemini Flash Lite | ベンチマーク |
| Embedding | text-embedding-3-large | text-embedding-004 | ベンチマーク |

**リスク:** 回答生成プロンプトは177行の複雑なルールベースであり、モデルのinstruction following能力に強く依存する。Gemini Flashで品質が不十分な場合、Gemini Proへの格上げまたはOpenAI APIの継続利用も選択肢として残す。

### 5.3 可用性

- 目標: 99%程度（確認中）

### 5.4 セキュリティ

- Cloud Armor（WAF / DDoS対策）
- Firebase Auth（認証）
- RBAC（Admin / Tenant Admin / Tenant User）
- 認可の責務分担: 認証済みセッション検証と粗いロール判定は ASP.NET Core middleware / authorization policy で先に実施し、対象データ依存の認可は Application 層でも再確認する
- テナント分離の二重防御: **EF Core global query filter（一次防御、アプリ層の WHERE 漏れ防止）+ RLS（最終防衛線、DB レベルで強制）**
- `SET LOCAL app.current_tenant_id` による transaction 冒頭の RLS session context 注入（コミット / ロールバックで自動消去）
- `tenant_id` / `clinic_id` 非正規化 + 複合 FK による整合性のDB制約化
- テナント/IP単位のレート制限
- 個人情報マスク: 電話番号・メールアドレスはルールベース（正規表現）で前段マスク、氏名・住所等はクエリ正規化LLMで後段マスクの二段構え。DB保存はマスク後のテキストのみ
- 個人情報は保持しない方針
- データ削除ポリシーを策定予定

### 5.5 データ保持

- 会話ログ: 全期間移行（確認済み）
- 削除ポリシー: 策定予定
- 医療系チャットボットのため患者の症状記述がログに残る可能性あり → 個人情報を持たない方針

## 6. 前提条件・制約

1. **開発体制**: 1名のシニアフルスタックエンジニアによる開発（AI活用前提）
2. **バックエンド**: C# 14 / .NET 10 (ASP.NET Core) on Cloud Run
3. **フロントエンド**: Next.js 16 / React 19 / TypeScript 6 on Vercel（TypeScript 7 は将来追従）
4. **DB**: Cloud SQL (PostgreSQL + pgvector)。DBアクセスはバックエンドAPI経由に一本化（アーキテクチャA）
5. **認証**: Firebase Auth
6. **AI**: Vertex AI（ベンチマーク結果に基づきモデル選定。OpenAI API継続も選択肢）
7. **管理画面統合**: F1-2（テナント管理画面）とF1-3（社内管理画面）は1つのNext.jsアプリとして統合実装（impersonation方式）
8. **最終スコープ**: クライアントと協議の上確定
