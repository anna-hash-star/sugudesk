> 作成日: 2026-07-02
> 対象: 株式会社exmore（SuguDesk / 医療採用ブースター）
> 位置づけ: 社内資料（ピッチデックver3・事業計画v4・pricing.md・要件定義書・採用ブースター資料・ギミック提携DPを踏まえた課題分析と戦略提言）

## 0. エグゼクティブサマリー

- exmoreは「患者接点AI（SuguDesk）→ BPO拡張 → AI事務長」という筋の良いストーリーと、健全な資本政策（シード後もFounder持分84%）を持つ。一方で、**シード期の最大リスクは市場でも競合でもなく「フォーカスの分散」と「計画前提の未検証」**にある。
- 現在走っているものは実質3事業＋1大型開発：①SuguDeskチャットボット、②BPO事務長代行、③医療採用ブースター（病院向け・新セグメント）、④GCPフル自社基盤へのリプラットフォーム。実働はCEO 1名＋業務委託エンジニア0.4FTE。**この体制で4本は成立しない。**
- 提言の核は3つ：
  1. **「クリニックのAI事務長」という1ストーリーに全事業を統合する。** 採用ブースターは別事業ではなく、**事務長代行事業の入口（仕掛け）**として位置づける。事務長代行は正面から売らず、採用で成果を出してから染み出す。病院セグメントも同じ階段の別の入口として設計する。
  2. **Series Aの物語を「ロゴ数」から「ARPA拡大のコホート証明（NRR）」に定める。** 41院のチャットボットより、15院でBPO転換30%・ARPA 3〜5倍・NRR130%のほうが強い。
  3. **全社KPI #1を「CS工数（時間/院/月）」に置く。** このビジネスの粗利とスケーラビリティはメンテ工数で決まる（pricing.mdの損益分岐は月17h）。プロダクト投資はCS工数を削る機能に限定し、リプラットフォームはスコープを縮小する。

## 2. 課題の構造分解

### 課題① フォーカスの分散（最重要）
SuguDesk運用・v2開発・BPO立ち上げ・採用ブースター（病院向け新規事業）・ギミック交渉・リプラットフォームが同時進行している。採用ブースターは**バイヤー（病院事務局）・商流・意思決定プロセス・セールスサイクルがクリニックと別物**で、実質的に新規事業の二重起動。シード期の死因第1位は「資金切れ」だが、その原因はほぼ常に「分散による全戦線の中途半端」である。

### 課題② 計画前提が未検証のまま採用先行
計画v4はM7から新規5件/月を置くが、その根拠であるギミック提携は未契約。BPO転換率5%/月、チャーン2%/月も実績ゼロの仮説。にもかかわらずM7からBPO事務長40万円＋オペ2名40万円＋CS35万円の**採用が「カレンダー基準」で計画されている**。売上前提が3ヶ月ずれるだけで、Phase2バーン234万円/月に対しランウェイは急速に削れる（計画上でもM13時点ランウェイ7.8ヶ月）。

### 課題③ 入口ARPAが低く、直販のユニットエコノミクスが成立しない
月8千〜1.5万円の商材をCEOが直販する構図は、CEOの時間コストを考えるとCACが回収不能。LTV（ARPA1.15万×チャーン2%→約50ヶ月）は約58万円＋導入費だが、**この価格帯はチャネル販売か、セールスレスな導入体験がないとスケールしない**。現状は「安い商材を高コストな売り方で売っている」。

### 課題④ 差別化が「価格1/4」= 弱いモート
GTM資料自身が「現在、競合優位性が低いプロダクト」と認めている。価格優位はGENOVA等の資本力あるプレイヤーに対して持続しない。本当のモート候補は「患者接点データ→FAQ資産→業務データベース→BPO提案根拠」の蓄積ループだが、**これはまだ構想であり、計測も商品化もされていない**。

### 課題⑤ BPOの労働集約性 — 「AIで1人10院」が未実証
ピッチデック自身が「事務長代行は最大手でも12年で300件、固定費型でスケールに苦戦」と指摘している。exmoreの反論は「AI＋データで1人が複数院を管理」だが、**現時点で1人あたり管理院数もCS時間/院も計測されていない**。これを数字で示せない限り、Series AでexmoreのBPOは「もう一つの事務長代行」に見える。またメンテ原価@1,200円/hの担い手（誰がその単価で安定供給されるのか）が不明確で、粗利77〜79%の再現性に疑義が残る。

### 課題⑥ ステージに対して過剰な技術投資
要件定義書は C#/.NET 10・CQRS-lite・Cloud Armor・LB・Firebase・pgvector のフル自社基盤を志向するが、顧客は4〜5件、開発リソースは0.4FTEの業務委託。**「100院スケール対応」を5院の段階で作り込むのは、シード資金の使途として順番が逆**。ボトルネックはインフラではなく、CS工数と販売チャネルにある。

### 課題⑦ セグメント集中リスクと「病院」への飛び地
現契約はほぼ美容・自由診療。保険診療・病院は単価・意思決定・要求水準が異なる。採用ブースターで狙う中小病院はARPAが高く魅力的だが、**クリニックで築いた資産（FAQデータ・導入事例・チャネル）がほぼ流用できない**。

## 3. 戦略提言

### 3.1 戦略の核：採用ブースターは「事務長代行の仕掛け」— 1つの階段に統合する

**事務長代行事業は正面から売らない。採用ブースターから仕掛ける。** 事務長代行を単体で提案しても「何を任せていいか分からない」「実績がない会社に経営中枢は預けられない」で止まる。採用で目に見える成果（採用決定・紹介費削減）を先に出し、その過程で院内オペレーションに入り込み、事務長代行へ染み出す。

```
        【入口は2つ、階段は1つ、頂上は「AI事務長」】

  Land A（クリニック）          Land B（中小病院）
  SuguDesk 患者接点AI           採用ブースター直販
  月1.5〜2.5万                  （採用ペイン最強・ARPA高）
       │                            │
       └────────────┬───────────────┘
                    v
  STEP 1: 採用ブースター＝事務長代行の入口（月8〜15万＋成果連動）
     「決まる病院」化：求人票・紹介会社リレーション・選考スピードKPI
                    │ 採用決定という“動かぬ成果”
                    v
  STEP 2: 染み出し（+5〜10万）
     定着フォロー（入職後30/60/90日）→ シフト・労務 → 集患
                    │ 院内オペの情報とアクセスが揃う
                    v
  STEP 3: フル事務長代行（月15〜35万）＝ AI事務長
     1人+AIで10院を運営
```

**なぜ採用が事務長代行の正しい入口なのか（この仕掛けの合理性）：**
1. **ペインが最強**：開業医の課題1位はスタッフ採用（開業医白書2025）。医療職求人倍率2.92倍。放置すれば病床稼働・受け入れ制限に直結する「事業継続の生命線」。
2. **ROIが数値で示せる唯一のBPO**：紹介フィー（看護師1人あたり年収の20〜30%＝約100万円前後）との比較で、月額費用が一目で正当化できる。事務長代行の価値は定性的だが、採用は「決定数」「紹介費削減額」で語れる。
3. **外部化への心理的抵抗が最も低い**：医療機関は既に紹介会社という外部を使い慣れている。経理・レセプトを他人に渡すより、採用支援を渡すほうがはるかに早い。
4. **実行過程が事務長代行の橋頭堡になる**：紹介会社へのレス代行・面接調整・条件設計・シフト前提の求人設計——採用を回すこと自体が院内オペの深部（労務・シフト・意思決定フロー）に触れる。信頼と情報が同時に貯まる。
5. **定着フォローで接点が常時化する**：入職後フォローは労務・教育・シフトの相談窓口化し、解約理由が消える。ここからフル代行への転換が自然につながる。
6. **プロトタイプ（本リポジトリ）が既に転換装置の形をしている**：紹介会社レスポンスKPI・滞留アラート・定着フォローの3機能は、まさに「採用→事務長代行」の階段の1〜2段目。

### 3.1b 採用→事務長代行の転換設計（Conversion Playbook）

仕掛けとして機能させるには、転換の段取りを最初から契約・オペレーションに埋め込む。

| 時期 | やること | 転換の仕込み |
|---|---|---|
| M0〜3 | 初期設計：求人票リライト・紹介会社リレーション構築・選考スピードKPI導入 | 院内の意思決定フロー・シフト・労務条件を棚卸し（＝事務長業務の可視化） |
| 採用決定時 | 定着フォロー（30/60/90日）を標準オプションとして提案 | 労務・教育への接点を獲得 |
| M6 | 「事務長業務診断」を無償実施（棚卸しデータがあるので工数は小さい） | フル代行の見積り提示 |
| M6〜 | フル事務長代行へ転換（月15〜35万） | SuguDesk未導入なら患者接点AIを逆クロスセル |

- 計測するKPI：採用決定数 / 選考リードタイム / 紹介費削減額（顧客向け価値指標）、**採用→事務長代行転換率・転換までの月数**（社内・Series A向け指標）。
- 事業計画v4への反映：現行は「事務長代行15万がM8〜、採用/集患5万がM13〜」の順だが、**実際の順序は逆**（採用が先行し、事務長代行が後から立ち上がる）。次版で入れ替える。
- **病院（Land B）は「別事業」ではなく「別の入口」**：ただし商流・意思決定が異なるため、最初の90日は有償エンゲージメント2〜3件（クリニック・病院合計）に絞り、「90日以内に採用決定を1件出せるか」を成果基準にする。無償PoCはやらない。

### 3.2 Series Aの物語：ロゴ数ではなく「ARPA拡大のコホート証明」

Series A投資家に見せるべきは以下の4点セット。41院のチャットボット導入より、この4つが揃った15院のほうが評価は高い。

| 証明したいこと | 目標（M18） | 現状 |
|---|---|---|
| Land：再現性ある獲得 | 15〜20院（うちチャネル経由50%+） | 4〜5院・全て直販 |
| Expand①：採用ブースター転換 | 導入6ヶ月以上の顧客の30%+が採用ブースター利用、採用決定 累計10名+ | 0（プロトタイプのみ） |
| Expand②：事務長代行転換 | 採用ブースター顧客の3〜5件がフル代行へ転換（転換率と月数をコホートで提示） | 0 |
| NRR / ARPA | 拡大コホートARPA 3〜5倍、NRR 130%+ | — |
| スケーラビリティ | CS工数/院/月を半減、1人あたり管理20院+ | 未計測 |

- ARRの目標は2,000〜3,000万円で十分（計画v4のY2 ARR1.14億は対外コミットにしない）。**「小さくても構造が証明されたエンジン」がSeries Aの調達力になる。**

### 3.3 GTM：チャネル分散と直販の役割変更

1. **ギミック提携をQ3中に「条件合意」まで持ち込む**。設計上の論点：(a)独占権は与えない（与えるなら最低コミット件数と引き換え）、(b)レベニューシェアは成果報酬型（送客→成約ベース）、(c)ギミックのブランドで売る場合もFAQデータの所有権はexmoreに残す。
2. **チャネルは最低3本並行で仕込む**（1本待ちにしない）：電子カルテ・予約システムベンダー、医療特化の税理士法人・開業コンサル（taxita等の資料が示す通り開業医の財布の入口を握っている）、医療モール運営・医師会。
3. **CEO直販は高ARPA案件専用にする**：プレミアム（多院）、病院、BPO商談のみ。ライト/スタンダード単品はチャネルとインバウンド（LP・事例・FAQページのSEO資産）に寄せる。

### 3.4 プライシング改定

1. **ライトプラン（月8千円）は新規販売を停止**。安いのに導入工数がかかり、拡張ストーリーにも乗らない。入口はスタンダードに一本化し、**月1.5万→2.5万円へ引き上げ、月次改善レポート＋改善提案（BPOの入口）を同梱**する。既存トラクション（電話20%削減）を根拠に値上げは正当化できる。
2. **初期費用を月額へ転嫁したサブスク型（初期0円・月3.5万・12ヶ月）を併設**。キャッシュフロー上は初期費用型が有利だが、チャネル販売では初期費用が最大の摩擦になる。
3. **採用モジュールは成果連動を混ぜる**（基本月額＋採用決定1名あたりフィー）。紹介会社フィー（年間1,139億円市場）との比較で圧倒的に安く見せられ、価値ベース価格に近づく。

### 3.5 プロダクト・開発戦略：「CS工数を削る機能」以外は作らない

- **全社KPI #1＝CS工数（時間/院/月）**。今週から計測を始める（工数記録がなければマージンもスケーラビリティも語れない）。
- 開発優先順位はこのKPIへの寄与順に並べ替える：
  1. 会話ログ→FAQ候補の自動生成・ワンクリック反映（セルフ改善アシスタント）
  2. 月次レポートの完全自動化
  3. 顧客セルフサーブのFAQ編集（exmoreが触らなくても鮮度が保たれる状態）
  4. HPクロール→自動ベクトル化（導入工数15〜40hの圧縮）
- **リプラットフォームはスコープ縮小**：Google Sheets脱却（Cloud SQL化）と認証の正常化は必須としてやる。一方、Cloud Armor/LB/CQRS/フルC#基盤は20〜30院まで後回し。マネージドサービスで凌ぎ、浮いた開発力を上記1〜4に振る。
- **創業エンジニアの採用（SO 5〜10%）を最優先の人事アジェンダにする**。夜間週末0.4FTEの業務委託は、単一障害点かつ「AIで効率化する会社」の技術的信用の欠落。チーム強化予算25%の使途はここに集中。

### 3.6 財務規律：採用は「カレンダー」でなく「トリガー」でゲート

| 計画v4の予定 | 提言：発動条件（トリガー） |
|---|---|
| M7〜 BPO事務長1名＋オペ2名採用 | BPO有償契約 3件成約 かつ 運用フローが文書化済み |
| M7〜 CS 1名（M10で2名） | 導入20院 または CS工数が月160hを超過 |
| M7〜 新規5件/月前提 | ギミック（または代替チャネル）契約締結後に計画へ反映 |

- 保守ケース（新規3件/月・BPO転換2.5%/月）でも**ランウェイ18ヶ月を常に確保**する。切りそうなら採用を止める、が原則。
- ブリッジ調達の選択肢（既存投資家のフォロー、公庫追加枠）はM12時点のKPIで判断できるよう、月次でOikazeにコホートデータを共有しておく。

## 4. 18ヶ月ロードマップ

### Phase A（M1〜M6, 〜2026年内）：仕掛けの1段目を成立させる
- 採用ブースター：既存SuguDesk顧客＋細木病院で**有償2〜3件を成約し、90日以内に採用決定1件以上**を出す ← 最重要。これが事務長代行事業の起点になる
- SuguDesk：新規は直販で+2件/月を維持（採用ブースターの母集団づくりとして位置づける）
- ギミック：条件合意→パイロット送客開始
- プロダクト：Sheets脱却＋セルフ改善アシスタント＋レポート自動化。CS工数計測開始。ブースターのプロトタイプは受注顧客の実運用に載せて磨く
- 採用：創業エンジニア1名クローズ
- 出口条件：**採用決定という成果が最低1件、かつ事務長業務の棚卸しデータが顧客2件分以上存在すること**

### Phase B（M7〜M12）：染み出しの実証
- 採用ブースター顧客に定着フォロー→労務・シフトの染み出しを開始し、**フル事務長代行への転換1〜2件目**を作る
- チャネル経由の初成約（ギミック or 代替チャネル）で新規4〜5件/月へ
- 転換率・NRR・CS工数/院を毎月計測し、拡大コホートARPA 3倍を実証
- トリガー充足を条件にBPO人員・CSを段階採用（採用するのは「事務長人材」より先に「採用オペレーション人材」）
- 出口条件：MRR 150〜200万円、NRR 120%+、採用→事務長代行の転換事例2件

### Phase C（M13〜M18）：Series Aの物語を完成させる

## 6. この戦略で変わること・変わらないこと

**変わらないこと**：「患者接点を握り、データと信頼でBPOへ拡張し、AI事務長へ」という根本仮説。シードで約束した「10院＋ARPA確立」のマイルストーン。

**変わること**：
- 3事業並走 → **1つの階段（SuguDesk → 採用ブースター → 事務長代行）**。事務長代行は正面から売らず、採用ブースターから仕掛ける
- ロゴ数至上 → **コホートで証明するNRR・ARPA拡大**（採用決定数と事務長代行転換率が中間指標）
- カレンダー採用 → **トリガー採用**
- フル基盤開発 → **CS工数削減に直結する機能だけ**
- 価格1/4という差別化 → **「入れると電話が2割減り、6ヶ月後に事務長業務が外せる」という価値の差別化**

シードの18ヶ月で証明すべきことはただ一つ：**「同じ顧客のARPAが、人を比例的に増やさずに5倍に育つ」**。それが数字で見えれば、Series Aは取りに行くものではなく、向こうから来る。
